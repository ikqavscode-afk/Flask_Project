# Публикация Flask Diary на Render

Руководство для первой публикации и дальнейших обновлений. Перед каждой выкаткой дополнительно проходится [чеклист](release-checklist.md). Аккаунт, подключение репозитория и действия в панели Render выполняет владелец проекта; результат проверяется командами из раздела 4.

## 1. Как это устроено

В репозитории лежит файл [`render.yaml`](../render.yaml) (Blueprint). Он описывает:

| Ресурс | Что это | Настройка |
|---|---|---|
| Веб-сервис `flask-diary` | сборка из `flask-diary/Dockerfile`, запуск gunicorn | тариф `free`, проверка здоровья `/health` |
| База `diary-db` | PostgreSQL 16 (та же версия, что проверяется в CI) | тариф `free` |
| Переменные | `APP_ENV=production`, `SECRET_KEY` (создаётся Render случайно), `DATABASE_URL` (берётся из базы), `PORT=10000`, `LOG_LEVEL` | секреты в файле не хранятся |
| Выкатка | `autoDeployTrigger: checksPass` | новая версия выкатывается только после зелёных проверок CI на GitHub |

При старте контейнера сначала применяются миграции базы (`flask db upgrade`), затем запускается сервер.

## 2. Важно знать до публикации (ограничения бесплатного тарифа)

Сверено с документацией Render ([free](https://render.com/docs/free), [web-services](https://render.com/docs/web-services)), 2026-11-11. Условия тарифов меняются: перед публикацией перепроверьте их в панели.

| Что | Ограничение | Последствие |
|---|---|---|
| Веб-сервис засыпает | после **15 минут** без запросов; пробуждение около минуты | первый запрос после паузы медленный; для демонстрации это нормально |
| Часы работы | **750 часов** в месяц на аккаунт | сервисы приостанавливаются до следующего месяца, если часы кончились |
| Локальные файлы | теряются при перезапуске | данные нельзя хранить в файлах; у нас всё в PostgreSQL |
| **Бесплатная база истекает** | **через 30 дней после создания**; ещё 14 дней на перевод на платный тариф, затем **база и все данные удаляются** | данные пользователей пропадут, если вовремя не перейти на платный тариф |
| **Бэкапов нет** | на бесплатной базе резервные копии не поддерживаются | восстановить данные после сбоя или удаления будет нечем |
| Размер и число | 1 ГБ; одна бесплатная база на аккаунт | для демонстрации достаточно |

### Решение, которое нужно принять до реальных пользователей

Требование сохранности данных проекта (потеря не более 24 часов, см. [requirements](requirements.md), NFR-12) **бесплатной базой не выполняется**. Варианты:

| Вариант | Когда подходит |
|---|---|
| **A. Демонстрационный режим**: оставить бесплатную базу, не хранить важных данных, предупредить пользователей, что данные могут исчезнуть через 30 дней, делать ручные копии (раздел 6) | показ работы приложения |
| **B. Платная база**: в `render.yaml` заменить `plan: free` у базы на платный тариф (актуальные названия и цены смотрите в панели Render) | реальные пользователи и настоящие данные |
| **C. Внешняя управляемая база** с бэкапами: только `DATABASE_URL` другого поставщика, код менять не нужно | если нужна бесплатная долгоживущая база |

Рекомендация: **A для первой публикации**, **B до появления реальных пользователей**. Решение записывается в журнал проверок.

## 3. Публикация (делает владелец)

1. Откройте https://dashboard.render.com и войдите через GitHub. При запросе доступа дайте приложению Render доступ только к репозиторию `Flask_Project`.
2. **New → Blueprint**, выберите репозиторий `Flask_Project`, ветку `main`. Render прочитает `render.yaml` и покажет два ресурса: `diary-db` и `flask-diary`. Если Render сообщит об ошибке в файле, скопируйте текст ошибки: он указывает, в какой строке проблема.
3. Нажмите **Apply**. Секретов вводить не нужно: `SECRET_KEY` создастся сам, а адрес базы подставится автоматически.
4. Дождитесь сборки образа и запуска (несколько минут). В разделе **Logs** сервиса должны появиться строки `Running upgrade ... initial schema` и запуск gunicorn.
5. Скопируйте адрес сервиса вида `https://flask-diary-….onrender.com`.

Адрес с HTTPS выдаёт сам Render. Свой домен можно подключить позже в настройках сервиса (раздел **Custom Domains**): код менять не нужно, заголовок HSTS и защищённые cookie уже работают по HTTPS.

## 4. Проверка после публикации

Замените `ADDRESS` на адрес сервиса. Если сервис спал, первая команда может занять около минуты.

```bash
curl -s https://ADDRESS/health                                  # {"status":"ok"}
curl -sI https://ADDRESS/home | grep -i -E "^(HTTP|strict-transport|content-security|x-frame|x-content|cache-control)"
curl -s -o /dev/null -w "%{http_code}\n" https://ADDRESS/       # 302: страница закрыта входом
curl -s -o /dev/null -w "%{http_code}\n" https://ADDRESS/нет-страницы   # 404
```

Ожидание: `/health` отвечает 200; в заголовках есть `Strict-Transport-Security`, `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`.

Вручную в браузере: регистрация → вход → создать карточку → найти → отредактировать → удалить через окно подтверждения → выход; вид на телефоне; пять неверных паролей подряд дают страницу «Слишком много попыток». В **Logs** должны быть записи о регистрации и входе без паролей. Результат записывается в журнал [чеклиста](release-checklist.md).

Проверка нагрузки против публикации не запускается: бесплатный тариф для неё не рассчитан. Для нагрузочных проверок нужен отдельный тестовый сервис.

## 5. Обновления и откат

- **Обновление:** изменения попадают в `main` только через pull request с зелёными проверками. Затем Render сам выкатывает новую версию (`checksPass`). Миграции базы применяются при старте контейнера, поэтому перед слиянием pull request с миграцией проверьте её на копии базы (см. чеклист, раздел 3).
- **Откат приложения:** в панели сервиса откройте историю выкаток (**Events** или **Deploys**) и верните предыдущую удачную версию (названия кнопок могут отличаться в новой панели). Если откатываемая версия работала со старой схемой базы, а новая миграция уже применена, сначала оцените, совместима ли старая версия с новой схемой; миграции с удалением колонок делаются в два релиза (см. [архитектуру](architecture.md)).
- **Остановка выкаток:** в настройках сервиса можно переключить автодеплой в `off`, это же можно сделать в `render.yaml` (`autoDeployTrigger: off`).

## 6. Резервные копии (вручную, пока база бесплатная)

В панели базы откройте раздел с параметрами подключения и возьмите **External Database URL** (внешний адрес). Не вставляйте его в файлы репозитория и в чаты: он содержит пароль.

```bash
export DATABASE_URL="…внешний адрес из панели…"
pg_dump -Fc -f "diary-$(date +%F).dump" "$DATABASE_URL"       # бэкап
createdb diary_check && pg_restore -d diary_check --no-owner diary-*.dump   # проверка на локальной копии
```

Процедура восстановления на копии проверена на PostgreSQL 18 (см. журнал чеклиста). Хранить файлы нужно вне репозитория (`*.dump` не коммитятся) и вне самого Render. Для регулярности делайте копию раз в сутки: так выполняется цель «потеря данных не более 24 часов». Не забудьте про срок жизни бесплатной базы (30 дней).

## 7. Чего не делать

- Не записывать пароли, адреса базы и ключи в репозиторий, журнал, сообщения и pull request.
- Не включать режим отладки (`FLASK_DEBUG`) на сервере.
- Не менять `SECRET_KEY` без необходимости: все текущие сессии пользователей станут недействительны.
- Не удалять базу в панели без свежей копии.
