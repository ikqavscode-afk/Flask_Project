# Публикация Flask Diary на Render

Руководство для первой публикации и дальнейших обновлений. Перед каждой выкаткой дополнительно проходится [чеклист](release-checklist.md). Аккаунт, подключение репозитория и действия в панели Render выполняет владелец проекта; результат проверяется командами из раздела 4.

## 1. Как это устроено

В репозитории лежит файл [`render.yaml`](../render.yaml) (Blueprint). Он описывает:

| Ресурс | Что это | Настройка |
|---|---|---|
| Веб-сервис `flask-diary` | сборка из `flask-diary/Dockerfile`, запуск gunicorn | тариф `free`, проверка здоровья `/health` |
| База `diary-db` | PostgreSQL 16 (та же версия, что проверяется в CI) | тариф `free` |
| Переменные | `APP_ENV=production`, `SECRET_KEY` (создаётся Render случайно), `DATABASE_URL` (берётся из базы), `PORT=10000`, `LOG_LEVEL` | секреты в файле не хранятся |
| Выкатка | `autoDeployTrigger: checksPass` | новая версия выкатывается только после зелёных проверок CI на GitHub |

При старте контейнера сначала применяются миграции базы (`flask db upgrade`), затем запускается сервер.

## 2. Важно знать до публикации (ограничения бесплатного тарифа)

Сверено с документацией Render ([free](https://render.com/docs/free), [web-services](https://render.com/docs/web-services)), 2026-11-11. Условия тарифов меняются: перед публикацией перепроверьте их в панели.

| Что | Ограничение | Последствие |
|---|---|---|
| Веб-сервис засыпает | после **15 минут** без запросов; пробуждение около минуты | первый запрос после паузы медленный; для демонстрации это нормально |
| Часы работы | **750 часов** в месяц на аккаунт | сервисы приостанавливаются до следующего месяца, если часы кончились |
| Локальные файлы | теряются при перезапуске | данные нельзя хранить в файлах; у нас всё в PostgreSQL |
| **Бесплатная база истекает** | **через 30 дней после создания**; ещё 14 дней на перевод на платный тариф, затем **база и все данные удаляются** | данные пользователей пропадут, если вовремя не перейти на платный тариф |
| **Бэкапов нет** | на бесплатной базе резервные копии не поддерживаются | восстановить данные после сбоя или удаления будет нечем |
| Размер и число | 1 ГБ; одна бесплатная база на аккаунт | для демонстрации достаточно |

### Решение, которое нужно принять до реальных пользователей

Требование сохранности данных проекта (потеря не более 24 часов, см. [requirements](requirements.md), NFR-12) **бесплатной базой не выполняется**. Варианты:

| Вариант | Когда подходит |
|---|---|
| **A. Демонстрационный режим**: оставить бесплатную базу, не хранить важных данных, предупредить пользователей, что данные могут исчезнуть через 30 дней, делать ручные копии (раздел 6) | показ работы приложения |
| **B. Платная база**: в `render.yaml` заменить `plan: free` у базы на платный тариф (актуальные названия и цены смотрите в панели Render) | реальные пользователи и настоящие данные |
| **C. Внешняя управляемая база** с бэкапами: только `DATABASE_URL` другого поставщика, код менять не нужно | если нужна бесплатная долгоживущая база |

Рекомендация: **A для первой публикации**, **B до появления реальных пользователей**. Решение записывается в журнал проверок.

## 3. Публикация (делает владелец): что, где и как

Названия кнопок сверены с документацией Render ([infrastructure-as-code](https://render.com/docs/infrastructure-as-code), [github](https://render.com/docs/github)), 2026-11-11. Если интерфейс изменился, ориентируйтесь на смысл шага. Платёжные данные, пароли и ключи вводит только владелец, в чаты и репозиторий они не передаются.

### Шаг 0. Проверка перед началом (1 минута)

Откройте в браузере https://github.com/ikqavscode-afk/Flask_Project/blob/main/render.yaml: файл должен быть в ветке `main`. Вход в GitHub должен быть под тем же аккаунтом, которому принадлежит репозиторий.

### Шаг 1. Аккаунт Render

1. Откройте https://dashboard.render.com.
2. Выберите вход через **GitHub** (Sign up / Sign in with GitHub) и подтвердите запрос GitHub на авторизацию. Если Render попросит подтвердить почту, подтвердите.
3. Если Render предложит создать рабочее пространство (workspace), оставьте предложенное имя.

Если Render запросит платёжную карту: для бесплатных ресурсов она обычно не нужна, но решение вводить ли её принимает только владелец. Бесплатные ресурсы можно создать и без платных функций.

### Шаг 2. Доступ Render к репозиторию

Откройте **New** (кнопка в правом верхнем углу панели) → **Blueprint**. Render покажет список репозиториев.

- Если `Flask_Project` в списке есть, переходите к шагу 3.
- Если нет, установите приложение Render для GitHub: https://github.com/apps/render/installations/new. Выберите свой аккаунт, в разделе **Repository access** выберите вариант с выбранными репозиториями (**Only select repositories**) и отметьте только `Flask_Project`, затем **Install**. Вернитесь в Render и обновите страницу.

Доступ позже можно изменить на той же странице: он нужен только для чтения кода и получения уведомлений о коммитах.

### Шаг 3. Создание Blueprint

1. На странице **New → Blueprint** нажмите **Connect** рядом с `Flask_Project`.
2. В форме:
   - **Blueprint Name**: любое понятное имя, например `flask-diary`;
   - **Branch**: `main`;
   - **Blueprint Path**: оставьте по умолчанию (файл `render.yaml` лежит в корне).
3. Откроется экран проверки изменений. Должны быть два ресурса:

   | Ресурс | Тип | Что должно быть указано |
   |---|---|---|
   | `diary-db` | база данных PostgreSQL | план Free, версия 16 |
   | `flask-diary` | веб-сервис | Docker, план Free |

   У сервиса переменные: `SECRET_KEY` помечена как создаваемая автоматически, `DATABASE_URL` берётся из `diary-db`, остальные заданы значениями. **Вводить ничего не нужно.**
4. Если вместо этого показан текст ошибки, скопируйте его целиком (он указывает строку `render.yaml`) и пришлите: публикацию продолжать не нужно.
5. Если всё верно, нажмите **Deploy Blueprint**.

### Шаг 4. Ожидание сборки и запуска

Откроется страница Blueprint с ресурсами. Нажмите на `flask-diary`.

- Сначала база `diary-db` получает статус «создаётся», затем «доступна» (обычно около минуты-двух).
- Сервис `flask-diary` собирает Docker-образ (первая сборка занимает несколько минут) и запускается. Прогресс: вкладка **Logs**.

В журнале запуска должны быть строки (порядок важен):

```
Running upgrade  -> f84d723fab19, initial schema
Running upgrade f84d723fab19 -> 10e5640c3870, login attempts
Listening at: http://0.0.0.0:10000
Booting worker with pid: …
```

Статус сервиса в итоге **Live**. Если вместо этого сборка или запуск упали, смотрите раздел «Если что-то пошло не так» ниже.

### Шаг 5. Адрес

Адрес сервиса показан вверху страницы `flask-diary`, под названием: `https://flask-diary-….onrender.com`. Откройте его в браузере. Если сервис «спал», подождите около минуты: Render показывает страницу загрузки.

### Шаг 6. Быстрая проверка в браузере (2 минуты)

1. Допишите к адресу `/health`: должно быть `{"status":"ok"}`.
2. Откройте адрес без пути: вас перенаправит на страницу входа.
3. Зарегистрируйтесь, войдите, создайте карточку, откройте её, нажмите «Удалить» (должно появиться окно подтверждения), выйдите.

Затем пришлите адрес сервиса: проверки из раздела 4 выполняются командами. Адрес секретом не является.

### Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| Экран проверки Blueprint показывает ошибку | Скопируйте текст ошибки целиком, не нажимайте Deploy Blueprint |
| Сборка падает | Вкладка **Logs**, этап сборки: скопируйте последние 30 строк |
| Сервис не становится Live, «порт не обнаружен» (no open ports detected) | Откройте **Environment** сервиса и проверьте, что `PORT=10000` |
| Проверка здоровья не проходит, `/health` отвечает 503 | Откройте **Logs**: причина обычно в подключении к базе; проверьте, что `diary-db` в статусе доступна |
| Сайт медленно открывается после паузы | Это бесплатный тариф: сервис просыпается около минуты |
| Приложение не запускается и пишет, что `SECRET_KEY` не задан или слабый | Откройте **Environment**: у `SECRET_KEY` должно быть значение; не заменяйте его коротким |

Никогда не публикуйте в чатах и в репозитории раздел **Environment** целиком и внешний адрес базы: в них есть пароль.

### Что происходит дальше автоматически

Render по умолчанию синхронизирует Blueprint при каждом пуше в ветку `main` (**Auto Sync**), а сервис выкатывается только после успешных проверок CI на GitHub (`autoDeployTrigger: checksPass`). Управлять синхронизацией можно на странице настроек Blueprint (Settings → Auto Sync), а ручную синхронизацию запускает кнопка **Manual Sync**.

## 4. Проверка после публикации

Замените `ADDRESS` на адрес сервиса. Если сервис спал, первая команда может занять около минуты.

```bash
curl -s https://ADDRESS/health                                  # {"status":"ok"}
curl -sI https://ADDRESS/home | grep -i -E "^(HTTP|strict-transport|content-security|x-frame|x-content|cache-control)"
curl -s -o /dev/null -w "%{http_code}\n" https://ADDRESS/       # 302: страница закрыта входом
curl -s -o /dev/null -w "%{http_code}\n" https://ADDRESS/нет-страницы   # 404
```

Ожидание: `/health` отвечает 200; в заголовках есть `Strict-Transport-Security`, `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`.

Вручную в браузере: регистрация → вход → создать карточку → найти → отредактировать → удалить через окно подтверждения → выход; вид на телефоне; пять неверных паролей подряд дают страницу «Слишком много попыток». В **Logs** должны быть записи о регистрации и входе без паролей. Результат записывается в журнал [чеклиста](release-checklist.md).

Проверка нагрузки против публикации не запускается: бесплатный тариф для неё не рассчитан. Для нагрузочных проверок нужен отдельный тестовый сервис.

## 5. Обновления и откат

- **Обновление:** изменения попадают в `main` только через pull request с зелёными проверками. Затем Render сам выкатывает новую версию (`checksPass`). Миграции базы применяются при старте контейнера, поэтому перед слиянием pull request с миграцией проверьте её на копии базы (см. чеклист, раздел 3).
- **Откат приложения:** откройте страницу сервиса **Deploys**, найдите недавнюю удачную выкатку и нажмите **Rollback**, затем на странице подтверждения **Rollback to this deploy** ([документация](https://render.com/docs/rollbacks)). **После отката из панели Render отключает автодеплой сервиса:** когда ошибка исправлена, включите его снова на странице **Settings** сервиса, иначе новые версии выкатываться не будут. Возможность отката на бесплатном тарифе документация прямо не описывает: проверьте при первой публикации и запишите результат в журнал. Если откатываемая версия работала со старой схемой базы, а новая миграция уже применена, сначала оцените совместимость; миграции с удалением колонок делаются в два релиза (см. [архитектуру](architecture.md)).
- **Остановка выкаток:** в настройках сервиса можно переключить автодеплой в `off`, это же можно сделать в `render.yaml` (`autoDeployTrigger: off`).

## 6. Резервные копии (вручную, пока база бесплатная)

В панели базы откройте раздел с параметрами подключения и возьмите **External Database URL** (внешний адрес). Не вставляйте его в файлы репозитория и в чаты: он содержит пароль.

```bash
export DATABASE_URL="…внешний адрес из панели…"
pg_dump -Fc -f "diary-$(date +%F).dump" "$DATABASE_URL"       # бэкап
createdb diary_check && pg_restore -d diary_check --no-owner diary-*.dump   # проверка на локальной копии
```

Процедура восстановления на копии проверена на PostgreSQL 18 (см. журнал чеклиста). Хранить файлы нужно вне репозитория (`*.dump` не коммитятся) и вне самого Render. Для регулярности делайте копию раз в сутки: так выполняется цель «потеря данных не более 24 часов». Не забудьте про срок жизни бесплатной базы (30 дней).

## 7. Чего не делать

- Не записывать пароли, адреса базы и ключи в репозиторий, журнал, сообщения и pull request.
- Не включать режим отладки (`FLASK_DEBUG`) на сервере.
- Не менять `SECRET_KEY` без необходимости: все текущие сессии пользователей станут недействительны.
- Не удалять базу в панели без свежей копии.
