# Чеклист перед выкаткой

## Правило

**Перед каждым деплоем, помимо рефакторинга и тестов, проводится проверка безопасности, тестирование, настройка окружения и подготовка инфраструктуры.** Это защищает данные пользователей и позволяет избежать критических сбоев в продакшене.

Как применять:

1. Пройти все пять разделов ниже по порядку.
2. Для каждого пункта указать результат: **выполнено** (с доказательством: команда, ссылка на запуск CI, отчёт), **отложено** (с причиной и сроком) или **не применимо** (с объяснением). Молча пропускать пункты нельзя.
3. Найденные проблемы исправляются до выкатки; критические (уязвимости, утечка секретов, потеря данных) блокируют релиз.
4. Результаты записываются в «Журнал проверок» в конце документа.

Статусы: ✅ сделано и проверено · ⚠️ сделано частично · ⬜ ещё не сделано.

## 3. База данных и данные

| Пункт | Как проверить | Статус |
|---|---|---|
| Бэкап боевой базы перед изменениями | см. «Репетиция релиза» ниже; на хостинге включить автоматические копии | ⚠️ процедура проверена, на хостинге не настроено |
| Миграции проверены на копии | `pg_dump` → копия → `flask db upgrade` → проверка данных | ✅ |
| План отката миграций | `flask db downgrade` на копии, данные сохраняются | ✅ |
| Автотест «миграции совпадают с моделями» | `tests/test_migrations.py` | ✅ |

### Репетиция релиза (проверено на PostgreSQL 18)

```bash
export PGHOST=… PGPORT=… PGUSER=…                      # реквизиты боевой базы (берутся из панели хостинга)
pg_dump -Fc -f backup.dump diary_prod                  # 1. бэкап
createdb diary_copy && pg_restore -d diary_copy --no-owner backup.dump   # 2. копия
DATABASE_URL=postgresql://…/diary_copy flask --app main db upgrade       # 3. миграция на копии
# проверить количество строк и работу приложения на копии
DATABASE_URL=postgresql://…/diary_copy flask --app main db downgrade     # 4. проверить откат
```

Боевая база при этом не затрагивается. Только после успешной репетиции выкатывайте релиз. Если нужно откатить уже выкаченную миграцию: `flask --app main db downgrade`, затем вернуть предыдущую версию приложения.

Правило для опасных миграций (удаление или переименование колонок): делать в два релиза, чтобы работающая версия не ломалась (см. [архитектуру](architecture.md)).

## 5. Мониторинг и план отката

| Пункт | Как проверить | Статус |
|---|---|---|
| Журнал событий | события входа, изменения данных и ошибки пишутся в stdout без паролей и личных данных | ✅ |
| Оповещения об ошибках | подключить Sentry или уведомления хостинга; проверка доступности `/health` внешним сервисом | ⬜ |
| План отката приложения | вернуть предыдущую версию: «Rollback» на хостинге либо `git revert` и повторная выкатка | ⬜ проверить на хостинге при первой публикации |

**План отката:** 1) остановить выкатку новых версий; 2) вернуть предыдущий образ или коммит (кнопка отката хостинга или `git revert <коммит> && git push`); 3) если релиз менял схему базы, выполнить `flask --app main db downgrade` на согласованную версию (только после проверки на копии); 4) убедиться, что `/health` отвечает 200 и ключевой сценарий работает; 5) записать причину и выводы в журнал проверок.
