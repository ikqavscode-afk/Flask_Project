# Архитектура Flask Diary

Документ описывает, как устроено приложение и как добавлять в него новые страницы, разделы и связи между данными, не ломая существующее.

## Принципы

1. **Раздел — это пакет.** Всё, что относится к одной функции сайта (маршруты, правила проверки, логика, шаблоны), лежит рядом.
2. **Маршруты тонкие.** Функция-маршрут принимает запрос, вызывает проверку и сервис, формирует ответ. SQL и бизнес-правил в ней нет.
3. **Логика в сервисах.** Сервис ничего не знает о запросах и шаблонах, поэтому его можно вызвать из теста, из командной строки или позже из REST API.
4. **Приложение создаёт фабрика.** `create_app()` собирает отдельный экземпляр: тесты не влияют друг на друга, настройки можно подменять.
5. **Схема базы меняется только миграциями.** Автотест падает, если модель изменили без миграции.

## Поток запроса

```
браузер → маршрут (views.py) → проверка (validation.py) → сервис (services.py) → модель (models/) → база
                    ↓
              шаблон (templates/<раздел>/)
```

| Слой | Где лежит | Отвечает за | Не должен |
|---|---|---|---|
| Маршруты | `diary/<раздел>/views.py` | запрос, `flash`, редиректы, журнал событий, выбор шаблона | содержать SQL и правила предметной области |
| Проверка | `diary/<раздел>/validation.py` | допустимые значения и сообщения об ошибках | обращаться к базе |
| Сервисы | `diary/<раздел>/services.py` | запросы к базе, правила, транзакции | использовать `request`, шаблоны, `flash` |
| Модели | `diary/models/*.py` | описание таблиц и связей | хранить логику запросов |
| Общее | `diary/core/` | страницы ошибок, `/health`, главная | зависеть от других разделов |

## Рецепт A. Новая страница в существующем разделе

Например, страница «Архив» в разделе карточек.

1. **Маршрут** в `diary/cards/views.py`: функция с `@bp.route('/archive')` и `@login_required`.
2. **Логика**, если нужна, в `diary/cards/services.py` (например, `list_archived(user_id, ...)`).
3. **Шаблон** `diary/templates/cards/archive.html` с `{% extends "base.html" %}`.
4. **Ссылка**: `url_for('cards.archive')` (имя = `<блюпринт>.<функция>`).
5. **Тесты**: вход обязателен (302 без входа), успешный показ, изоляция данных пользователей.

## Рецепт B. Новый раздел

Например, «Напоминания».

1. Создайте пакет `diary/reminders/` с файлами `__init__.py`, `views.py`, `services.py`, `validation.py` по образцу `diary/cards/`. В `views.py`: `bp = Blueprint('reminders', __name__)`; в `__init__.py`: `from .views import bp`.
2. Шаблоны: `diary/templates/reminders/`.
3. Подключите блюпринт одной строкой в `_blueprints()` в `diary/__init__.py`.
4. Если нужны таблицы, выполните рецепт C.
5. Тесты `tests/test_reminders.py` (фикстуры `app` и `client` уже есть).

Адреса и имена маршрутов существующих разделов не меняйте без необходимости: на них ссылаются шаблоны и пользователи.

## Рецепт C. Новая сущность и связь между данными

Например, теги для карточек (многие ко многим).

1. **Модель** `diary/models/tag.py`:

   ```python
   from ..extensions import db

   card_tags = db.Table(
       'card_tags',
       db.Column('card_id', db.ForeignKey('card.id', ondelete='CASCADE'), primary_key=True),
       db.Column('tag_id', db.ForeignKey('tag.id', ondelete='CASCADE'), primary_key=True),
   )

   class Tag(db.Model):
       __tablename__ = 'tag'
       __table_args__ = (db.UniqueConstraint('user_id', 'name'),)

       id = db.Column(db.Integer, primary_key=True)
       name = db.Column(db.String(30), nullable=False)
       user_id = db.Column(db.Integer, db.ForeignKey('users.id'), nullable=False)
       cards = db.relationship('Card', secondary=card_tags, back_populates='tags')
   ```

   В `Card` добавьте `tags = db.relationship('Tag', secondary='card_tags', back_populates='cards')`. (строка `'card_tags'` вместо переменной, чтобы не импортировать модуль тегов в модуль карточек).
2. **Импорт** новой модели в `diary/models/__init__.py` (иначе Alembic её не увидит).
3. **Миграция**: `flask --app main db migrate -m "tags"`, затем прочитайте созданный файл в `migrations/versions/`, проверьте `upgrade` и `downgrade` и примените `flask --app main db upgrade`.
4. **Права доступа**: у каждой пользовательской сущности есть `user_id`, а запросы всегда фильтруются по нему (см. `get_user_card_or_404`). Связи не должны позволять увидеть чужие данные.
5. **Сервис и проверка** в разделе, который владеет логикой.
6. **Тесты**: создание, чужие данные недоступны (404), удаление связанных строк, миграция вверх и вниз.

Для изменений, ломающих схему (удаление или переименование колонок), делайте два релиза: сначала добавьте новое и перейдите на него, потом удалите старое. Так работающая версия не ломается во время выкатки.

## Готовность нового функционала (чек-лист)

- [ ] Тесты на успешный сценарий, ошибки и граничные случаи; весь набор зелёный.
- [ ] Миграция, если менялась схема; тест `test_migrations_match_models` проходит.
- [ ] Данные проверяются на сервере (`validation.py`), ограничена длина.
- [ ] Страница закрыта `@login_required`, данные фильтруются по владельцу.
- [ ] Каждая форма с `POST` содержит `csrf_token`; изменяющие действия не выполняются через `GET`.
- [ ] В журнал не попадают пароли, токены и содержимое пользовательских записей.
- [ ] Интерфейс: контраст не ниже 4,5:1, виден фокус, нет горизонтальной прокрутки на 375 px, у картинок есть `alt`.
- [ ] README или этот документ обновлены, если изменились запуск, структура или правила.

## Масштабирование при росте нагрузки

- **Процессы**: gunicorn запускается с несколькими процессами; состояние (например, счётчик попыток входа) хранится в базе, а не в памяти.
- **База**: PostgreSQL; для SQLite нагрузка ограничена.
- **Здоровье**: `/health` для хостинга, журнал в стандартный вывод.
- **Когда понадобится**: общий кэш (например, Redis) для частых чтений, очередь задач для медленных операций, отдельная раздача статики через CDN. Слой сервисов позволяет добавить REST API без переписывания логики.
