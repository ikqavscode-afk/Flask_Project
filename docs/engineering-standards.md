# Стандарты разработки

## Правило

**Любая работа над кодом, приложениями, сайтами и тестами ведётся по жизненному циклу разработки (SDLC) и принципам ниже.** Ни один этап не пропускается молча: он либо выполнен (с доказательством), либо отложен с причиной и сроком, либо неприменим (с объяснением). Перед выкаткой дополнительно проходится [чеклист](release-checklist.md).

Статусы: ✅ выполняется и проверено · ⚠️ частично · ⬜ ещё не сделано.

## 1. Жизненный цикл

| Этап | Что делаем | Где в проекте | Статус |
|---|---|---|---|

| Проектирование | стек, слои, схема компонентов, рецепты расширения; API проектируется до реализации | [architecture.md](architecture.md) | ✅ (API нет) |

| Разработка | небольшие итерации, сначала минимальный работающий продукт (MVP) | план по спринтам, один коммит — одно изменение | ✅ |

| Поддержка и мониторинг | логи и метрики в реальном времени, быстрое исправление, обратная связь | журнал в stdout, `/health` | ⚠️ нет оповещений |

## 2. Принципы кода

| Принцип | Что значит у нас | Как проверяем |
|---|---|---|
| **KISS** | простое решение, архитектура без «задела на будущее»; сложность функции не выше 8 | `ruff` (правило C901) в CI |
| **DRY** | логика не повторяется; фрагмент встретился третий раз — выносим | `pylint --enable=duplicate-code`; обзор |
| **YAGNI** | не пишем «про запас»: код без использования удаляем | `vulture --min-confidence 60 --ignore-decorators "@bp.route,@login_manager.user_loader"` |
| **SOLID** | один модуль — одна ответственность; расширение без правки существующего; зависимость от абстракций там, где это окупается | обзор по чек-листу PR |
| **Git** | весь код в репозитории; понятные сообщения коммитов | см. раздел 4 |
| **Обзор кода** | ничего не попадает в `main` без проверки | см. раздел 4 |

## 4. Git, ветки и обзор кода

**Стратегия:** основная ветка `main` всегда в рабочем состоянии. Изменения делаются в короткоживущих ветках (`feature/…`, `fix/…`, `chore/…`), попадают в `main` через запрос на слияние (pull request) и только после зелёных проверок CI. Слияние с объединением коммитов (squash).

**Сообщения коммитов:** тема на английском в повелительном наклонении, до 72 символов, с областью в начале при необходимости («Diary: …», «CI: …»); в теле, если нужно, объяснение *зачем*, а не *что*.

**Обзор кода:** ни одна строка не попадает в `main` без проверки. В команде проверку делает второй человек. При работе в одиночку обзор заменяют автоматические проверки CI плюс обязательная самопроверка по чек-листу в шаблоне pull request (`.github/pull_request_template.md`), выполненная после паузы, а не сразу после написания. Правила ветки `main` на GitHub (Settings → Branches): требовать pull request и успешные проверки `lint`, `security`, `flask-apps`, `diary-postgres`, `cli-shop`, `algorithms`, `docker`; запретить прямую отправку.

### Состояние на сегодня (2026-11-11)

- Сообщения коммитов осмысленные, изменения идут через ветки и pull request со слиянием squash (#9, #10).
- **Защита ветки `main` включена:** слияние только через pull request, обязательны 12 проверок CI (`lint`, `security`, `flask-apps` ×4, `diary-postgres`, `cli-shop` ×2, `algorithms` ×2, `docker`), ветка должна быть актуальной перед слиянием, история линейная, принудительная отправка и удаление ветки запрещены. Обязательных одобрений нет (работа ведётся одним человеком); владелец сохраняет возможность обойти правила только в аварийной ситуации, и каждый такой случай нужно записывать в журнал проверок.
- Отклонение, найденное при проверке: pull request #9 был слит без ожидания проверок последней правки. Теперь это невозможно без обхода правил.
- Триггер CI исправлен: проверки ветки идут один раз (через pull request), а `push` считается только для `main`.

## 5. Перед каждым изменением

1. Требование записано (или это исправление ошибки с воспроизводящим тестом).
2. Ветка создана, изменение небольшое.
3. Тесты и линтер зелёные локально; затем зелёный CI.
4. Самопроверка по шаблону pull request; обновлена документация.
5. Для выкатки пройден [чеклист](release-checklist.md).
