# Руководство по разработке

## Подготовка

Нужна Python 3.12 или новее. Инструменты разработки (тесты, покрытие, линтер) ставятся из одного файла с зафиксированными версиями:

```bash
cd flask-diary                         # или другой проект
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -r ../requirements-dev.txt
```

## Проверки перед коммитом

Из корня репозитория:

```bash
ruff check .            # линтер
ruff format .           # форматирование (ruff format --check . только проверяет)
```

Из папки проекта:

```bash
pytest -q --cov=diary --cov-fail-under=95   # Flask Diary
pytest -q --cov=shop --cov-fail-under=90    # CLI Shop
pytest -q --cov=dp --cov-fail-under=95      # Algorithms
```

Те же проверки выполняет CI на GitHub: коммит не считается готовым, пока все задачи зелёные.

Чтобы проверка запускалась автоматически перед каждым коммитом, один раз выполните `pre-commit install` (пакет `pre-commit` ставится отдельно, настройки уже лежат в `.pre-commit-config.yaml`).

## Порядок работы с изменениями

Работа ведётся по [стандартам разработки](docs/engineering-standards.md): жизненный цикл, принципы KISS, DRY, YAGNI, SOLID, безопасность с первого дня, CI/CD, документация, резервное копирование.

```bash
git switch -c feature/короткое-описание        # новая ветка от актуального main
# … изменения, тесты, ruff …
git push -u origin feature/короткое-описание
gh pr create --fill                             # pull request с чек-листом самопроверки
```

В `main` изменения попадают только через pull request после зелёных проверок CI: ветка `main` защищена на GitHub, прямые отправки и слияние с красными проверками запрещены. Сливайте командой `gh pr merge <номер> --squash --delete-branch` **после** того, как все проверки позеленели.

## Правила

- **Один коммит — одно законченное изменение** с понятным сообщением на английском в повелительном наклонении («Add…», «Fix…», «Refactor…»).
- **Тесты вместе с кодом.** Для исправления ошибки сначала напишите тест, который её воспроизводит.
- **Тесты не трогают рабочие данные.** Используйте фикстуры `app` и `client`: база создаётся в памяти.
- **Секретов в репозитории нет.** Ключи и пароли только в переменных окружения; в репозитории лежит лишь `.env.example`.
- **Схема базы меняется миграциями.** После изменения моделей создайте и проверьте миграцию (см. [архитектуру](docs/architecture.md)).
- **Не меняйте адреса страниц и имена маршрутов без необходимости.**

## Перед выкаткой (обязательное правило)

Перед каждым деплоем, помимо рефакторинга и тестов, проводится проверка безопасности, тестирование, настройка окружения и подготовка инфраструктуры. Все пункты проходятся по [чеклисту](docs/release-checklist.md), результат записывается в его журнал проверок. Критические проблемы (уязвимости, утечка секретов, риск потери данных) блокируют релиз.
